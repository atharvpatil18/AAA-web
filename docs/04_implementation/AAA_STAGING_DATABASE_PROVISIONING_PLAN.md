## 3. Granular Provisioning Specifications

### 3.1 Region & Data Residency Confirmation
- **Designated Region:** **AWS `ap-south-1` (Mumbai, India)**.
- **Statutory Justification:** Complies with Section 9 and Section 16 of the Digital Personal Data Protection (DPDP) Act 2023, ensuring all synthetic staging records and future student records reside within Indian territorial borders.
- **Provider Guarantee:** Supabase confirms physical database storage in AWS Mumbai data centers.

### 3.2 Access Control & Role Permission Design
The staging database utilizes PostgreSQL Role-Based Access Control (RBAC):

| PostgreSQL Role | Access Scope | Usage in Staging | Security Control |
| :--- | :--- | :--- | :--- |
| **`postgres`** | Database Administrator / Superuser | Applying migrations, managing extensions, schema maintenance. | Password protected; restricted to Nitin Patil via SSL only. |
| **`service_role`** | Bypass RLS / Backend Execution | Edge Function (`/api/discovery-intake`) executing stored procedures. | Server-side environment variable only; never exposed in client bundles. |
| **`authenticated`** | Logged-in Users (JWT verified) | Future authenticated student session queries. | Bound to Supabase Auth JWT validation; RLS policies enforced. |
| **`anon`** | Unauthenticated Public API | Public visitor interaction (e.g. course catalogs). | Strictly read-only on whitelisted public views; blocked from `micro_batches`. |

### 3.3 Zero-PII & Production Isolation Guarantee
- **Hard Rule:** Under no circumstances shall real parent phone numbers, parent names, student competition results, or production credentials be migrated or copied to the staging instance.
- **Data Fixtures:** All testing will use synthetic records generated by `createSyntheticLead()` (e.g. `rohan.parent@example.com`, `9823012345`, `AAA-LEAD-2026-TEST-0001`).

## 4. Migration Application Procedure

### Step 1: Pre-Migration Health Check
Connect via PostgreSQL CLI to confirm clean database state:
```bash
psql "sslmode=require host=db.<STAGING_REF>.supabase.co user=postgres dbname=postgres" \
  -c "SELECT version();"
```

### Step 2: Apply Migration Script
Apply the version-controlled migration file [`supabase/migrations/20261105_micro_batches_cap_constraint.sql`](file:///c:/0-ATHARV2NITIN_Projects/AAA_WEB/supabase/migrations/20261105_micro_batches_cap_constraint.sql):
```bash
psql "sslmode=require host=db.<STAGING_REF>.supabase.co user=postgres dbname=postgres" \
  -f "supabase/migrations/20261105_micro_batches_cap_constraint.sql"
```

### Step 3: Verify Schema & Constraint Creation
```sql
-- 1. Verify micro_batches table exists with check constraint
SELECT conname, pg_get_constraintdef(oid) 
FROM pg_constraint 
WHERE conname = 'chk_max_batch_capacity';

-- 2. Verify batch_enrollments table exists with unique constraint
SELECT conname, pg_get_constraintdef(oid) 
FROM pg_constraint 
WHERE conname = 'uq_batch_student';

-- 3. Verify stored procedure is compiled and secure
SELECT proname, prosecdef FROM pg_proc WHERE proname = 'enroll_student_into_batch';
```

## 5. Rollback Strategy

If any failure occurs during staging migration testing, the following rollback script restores the staging database to a clean slate without residual locks or tables:

```sql
-- ==============================================================================
-- AAA STAGING ROLLBACK SCRIPT (EMERGENCY TEARDOWN)
-- ==============================================================================
BEGIN;

-- 1. Drop Stored Procedure
DROP FUNCTION IF EXISTS public.enroll_student_into_batch(VARCHAR, VARCHAR, VARCHAR, VARCHAR, VARCHAR);

-- 2. Drop Dependent Enrollments Table
DROP TABLE IF EXISTS public.batch_enrollments CASCADE;

-- 3. Drop Micro-Batches Table
DROP TABLE IF EXISTS public.micro_batches CASCADE;

COMMIT;
```
